# Architecture

[README](README.md) · [Contributing](CONTRIBUTING.md) · [Code standards](docs/code-standards.md) · [Self-hosting](docs/self-hosting.md)

Calends is a single-owner ledger with two web entry points and one Worker backend. React renders the interface; shared TypeScript calculates billing and financial metrics; D1 provides the persistence API. Docker runs the same Worker locally with SQLite, rather than a separate server implementation.

## Runtime map

```mermaid
flowchart LR
    Public[Public page /public] --> PublicAPI[GET /api/public]
    App[Calends app /] --> API[Authenticated /api/*]
    Client[MCP client] --> MCP[Bearer-authenticated /mcp]
    API --> Store[worker/store.ts]
    PublicAPI --> Store
    Store --> DB[(D1 or local SQLite)]
    PublicAPI --> Mask[shared/mask.ts]
    Mask --> Public
    MCP --> Tools[worker/ai/mcp-tools.ts]
    Assistant[In-app assistant] --> Tools
    Tools --> Store
    API --> Domain[shared billing and phases]
    Tools --> Domain
    App --> Domain
    Public --> Domain
    Cron[Scheduled handler] --> Notify[Reminders and FX refresh]
    Notify --> Store
    Notify --> Domain
```

Arrows show calls or response flow, not separate services. The public API checks whether sharing is enabled before returning masked state. Browser sessions and MCP bearer tokens are independent authentication mechanisms. A configured `BASE_PATH` prefixes these routes; examples below assume a root deployment.

## Web requests and state

`app/src/main.tsx` loads the public entry for `/public` and `app/src/app.tsx` for application pages and `/login`. These bundles have separate component and style trees. The app uses shared components in `app/src/components/`; the public page uses `app/src/public/`. The public page first renders its skeleton in the visitor's browser language, then switches to the owner's language from `/api/public` (`settings.language`, else the owner's last used `languageSeen`). It falls back to the current language if that bundle fails to load. It shows each subscription's own price: `maskForPublic` in [shared/mask.ts](shared/mask.ts) omits shared-plan data, so a plan fully covered by members does not appear as zero and member shares and payment status stay private; private pages still count only the owner's share.

`Settings.publicPage` customizes the public page: browser title, bio, its own avatar, whether visitors see the theme button (`themeButton: false` hides it; the currency switch is not configurable), each widget's visibility and position on a 12-column grid (`x`, `y`, `w`, `h`), and any number of metric cards. Absent means the default page. [shared/public-layout.ts](shared/public-layout.ts) owns the widget registry, minimum widths, layout rules and validation; calendar, subscription years, tenure, spending map, changes and monthly change start off and appear only when added, and each metric card stores a template (`number`, `trend`, `compare`, `share`, `rows`) and metric ids that [shared/public-metrics.ts](shared/public-metrics.ts) resolves. Widgets read the masked state only, through [shared/treemap.ts](shared/treemap.ts), [shared/calendar.ts](shared/calendar.ts), [shared/public-changes.ts](shared/public-changes.ts) and `yearsTimeline` in [shared/gantt.ts](shared/gantt.ts); changes use a whitelist and never carry event notes. `checkSettings` validates writes, and the field is not exposed to MCP. A page without saved positions, including one that only hides sections, keeps the flow layout: each row's last card fills the row, tablets use half or full width and phones one column. A placed page uses those cells from 1024px up and one column in `y`, `x` order below, where non-`rows` metric cards up to 4 columns wide sit two to a row; `h` is a minimum, so a card with more content grows its rows instead of clipping, and rows held only by a card with no data collapse. Dragging records each card's current content height, and that minimum stays after the content shrinks until the owner resizes the card. Cards use container queries because their width no longer follows the viewport. The footer and icon pile stay at the bottom and can only be hidden. `publicTitle` keeps the header title. The browser title is set by JavaScript, so link previews and crawlers still see `Calends`.

[PublicPageEditor](app/src/views/PublicPageEditor.tsx) at `/settings/public` edits a draft and writes it only on Save; it warns before closing the page or following an in-app link with unsaved changes (the browser back gesture is not intercepted). Its preview is an iframe of `/public?preview` driven by same-origin `postMessage`: the editor masks the ledger in the browser with `maskForPublic(state, { untrimmed: true })` and posts the result plus the draft, so preview uses real data with no new endpoint and works while the public page is off. At desktop width the frame renders [Canvas](app/src/public/canvas.tsx): cards are dragged and resized inside the frame and the result is posted to the editor on release, then normalized with `publicGrid`; with auto-snap on (the default, `autoSnap: false` turns it off, editor-only and not sent to visitors) every edit in the draft moves all cards up so no empty rows remain, and a dragged card swaps order once its leading edge passes another card's middle; saved pages change only after an edit and Save. With auto-snap off a drop pushes overlapped cards down and leaves other gaps in place, and removing a card from a placed page collapses only the rows it held alone. A drag that ends where it started changes nothing. The page header sits outside the grid and is edited in the frame as well: name and bio in place, avatar through a side inspector, and a click on the theme button hides or restores it for visitors. Each change is posted to the editor's draft at once. Without a canvas (narrow, touch or phone preview) those fields stay in the side column. The side column is a widget library with thumbnails: an item is dragged onto the frame (the parent posts `PUBLIC_PREVIEW_DROP`) or clicked to add it at the bottom, and selecting a metric card swaps the column for that card's template and data. A widget with no data shows a placeholder in the canvas and takes no space for visitors. Narrow windows, touch devices and the phone preview are read-only. Outside a same-origin frame `?preview` has no effect.

Independent facts in translation templates use newlines; [copyParts](app/src/components/copy.tsx) renders them as separate, wrapping elements with spacing. It does not split punctuation in user-provided names. `title` strings retain line breaks: [installTitleTips](app/src/components/title-tips.ts) renders every `title` in both bundles through a shared tip, blanking the attribute while it shows so the system tooltip stays away, and restoring it afterwards unless the component changed it meanwhile.

Application title/hint pairs use `CardTitle` and circular actions use `IconButton` in [ui.tsx](app/src/components/ui.tsx), with alignment, responsive hit areas and interaction states owned by [ui.css](app/src/components/ui.css). `Hint` uses a React Aria tooltip portal with keyboard and press activation, viewport collision handling and Escape dismissal. Chart and period tips retain the shared `TipLayer`; unmounting an older app instance only unregisters its own setter, so a language remount keeps the new binding. `TipLayer` measures its content and clamps/flips it inside the viewport; scrolling, resizing or Escape dismisses it. Control heights in both style trees use [shared size tokens](app/src/control-sizes.css); adjacent actions share one tier, including on narrow/coarse-pointer screens (see [UI standards](docs/code-standards.md#ui-and-translations)). Public cards and icon actions implement the equivalent layout rules inside the public style tree without importing application styles. Collapsed sidebars are inert. Narrow screens (≤860px, including PWA standalone) replace the sidebar, which stays in the DOM but inert and hidden, with the floating dock in [MobileNav.tsx](app/src/components/MobileNav.tsx): a capsule of four module entries plus a round More button. More slides the capsule away and opens two 90° arcs anchored on the button: currency, theme and settings on the inner arc; the remaining modules and New on the outer arc. Except for the wallet grid’s dashed New card, the More arc owns page creation on phones: a page that passes `onAdd` to `Toolbar` (people, sharing, behalf) registers it through [page-add.ts](app/src/page-add.ts), and New runs that page's add instead of a plain new subscription. Mobile toolbars draw no search or add buttons; the subscriptions page keeps its own search field, and the wallet page ends its card grid with a dashed New card. Assistant and Connect merge into one AI entry there, with an Assistant | Connect switch in both toolbars when both are available. [mobile-nav.ts](app/src/mobile-nav.ts) takes the first four modules visible in the sidebar, in the sidebar's order, so the sidebar's order and visibility settings drive both; with fewer modules the capsule simply holds fewer entries. Older ledgers may still store a `bottomNav` setting, which is ignored. At 640px and wider (tablets, landscape) the capsule holds every visible module, so More keeps only currency, theme, settings and New. On narrow screens only the page title stays pinned at the top (opaque under the status bar, frosted below); `Toolbar` renders its switch and actions in a `.tb-under` row that scrolls away with the page. The bar hides while a coarse-pointer text input has focus; desktop renders none of it.

Sheet-level circular actions use the `Sheet.actions` header slot immediately before Close, including bare subscription details. [CopyImageButton](app/src/components/CopyImageButton.tsx) owns image clipboard support, pending state and localized success/failure feedback; it passes a PNG promise to `ClipboardItem` synchronously in the click handler for Safari. Existing detail, calendar-report, share-poster and masked carpool renderers retain their capture boundaries. Overview and report cards mark `data-copy-card`; [snapshotCard](app/src/snapshot.ts) captures only that card at its visible dimensions and scroll offsets. Image actions fade in on card hover or keyboard focus and stay faintly visible on touch; crowded control rows omit the extra action. Snapshot rendering always excludes `data-snapshot-hide`; card exports additionally omit selectors, hints and navigation controls while retaining chart labels and data. These actions do not change ledger state or masking rules.

Keyboard routing in [keyboard.ts](app/src/keyboard.ts) is shared by the app and calendar. Single-key actions pause in editable controls, during IME composition, with modifiers (except Shift for `?`), or while overlays are open. `N` creates a subscription, `1–9` follow visible sidebar order, `/` focuses the current page search or opens the palette, and `?` opens the localized shortcut sheet. In subscription details only, `E` follows the Edit button's return-to-details path; nested overlays block it. Command/Control+K opens search and Command/Control+B (also Command/Control+\) toggles the sidebar. Calendar arrows change month (year in year view) and `T` returns to today.

[Sheet](app/src/components/overlays.tsx) handles Enter in writable single-line inputs and Command/Control+Enter or Command/Control+S at any focus, clicking the enabled footer primary button of the topmost sheet. Sheets form one stack: only the topmost is visible (covered scrims are hidden, not unmounted), and a sheet opened above another shows a back button in place of close, so users see one layer at a time. A nearest `data-submit` region selects its own action; an empty value delegates to a local handler without falling through to the footer. These boundaries isolate member receipts, copied receipts, plan changes and inline price/account edits. Open pickers, IME composition and repeated keys never submit. Plain Enter retains native behavior in textareas, buttons, links and selection controls. Command/Control+S always suppresses browser Save, even outside sheets. Record deletion, token revocation and passkey removal use [ConfirmButton](app/src/components/ConfirmButton.tsx): the first click arms a red capsule, the second executes; blur, Escape or four seconds cancel the armed state. Consequence text is retained in its hint. Reference migration still requires choosing a target before the final deletion action. Other confirmation dialogs retain native focused-button Enter and React Aria Escape dismissal, with Cancel focused initially.

Application routes are `/overview` (overview), `/list`, `/calendar`, `/report`, `/wallet`, `/family`, `/family/people`, `/behalf`, `/assistant`, `/connect` (AI access), `/settings`, `/settings/public` (public page editor) and `/cat/<category>`. Unauthenticated visits to application pages redirect to `/login?next=<route>`, with the original app route URL-encoded in `next`; successful login returns to that page. For example, `/wallet` redirects to `/login?next=wallet`. An unauthenticated visit to `/` goes to `/public` when public sharing is enabled in Settings, otherwise to `/login`. The read-only `/public` page is available only when public sharing is enabled. An authenticated visit to `/` redirects to the configured start page, defaulting to `/overview` when none is set or the configured page is unavailable.

Local detail stress verification uses the isolated Worker/Vite lifecycle in [detail layout stress captures](CONTRIBUTING.md#detail-layout-stress-captures). Vite accepts an optional API origin and optimizer cache directory for this workflow; normal development defaults are unchanged.

The browser core in `app/src/store.ts` owns synchronization and shared write/revision counters. `auth.ts` and `ledger-writes.ts` bind their operations to that core through explicit functions; `prefs.ts` owns local preference subscriptions and mirroring without importing the store, so the public page stays independent of private state. `toast.ts` owns feedback and clipboard handling. The app boots through `boot()` in `app/src/store.ts`, showing cached state when available and then requesting `/api/state`. Authenticated state contains subscriptions, payment methods, settings, people, preferences and current/historical FX. Unauthorized responses and sign-out share one cleanup: they return the browser to login and remove the private ledger cache, offline data cache, local assistant chat, editor drafts and pending assistant hand-off, keeping display preferences and language. Browser storage keys carry the `BASE_PATH` suffix through `storageKey()`; a subpath install still reads an older unprefixed key once as a fallback. If the first load fails and no cached ledger exists, the app shows an offline notice with a retry action rather than the login form; a rendering error replaces the app with a reload notice from the root error boundary. Optimistic writes use the same store and reconcile against server results: saved subscriptions and payment methods take the record the server returns, and a failed write rolls back locally and then forces a full snapshot once no writes are pending, so a rollback cannot hide another write that succeeded meanwhile. Saving an edit form whose record was deleted elsewhere fails instead of recreating it. Browser cache is not the durable ledger. Preference writes swap only `state.prefs` and keep the ledger object identity, so derived financial values memoized on `state` survive view, zoom and layout changes; `usePref()` subscribers update by value. Overview and the subscription list load with the shell; calendar, wallet, connect, annual review and assistant views are lazy chunks prefetched when the browser is idle after state loads.

`Settings.signedAmounts` defaults to enabled when absent. The app root applies it through `setSignedAmounts()` in [shared/format.ts](shared/format.ts) and remounts the app when it changes, as for locale changes. `flow()` formats directed cash flows (negative outflows, positive inflows); prices, balances and comparisons retain their own formatting. This display-only setting uses the existing settings JSON persistence and does not change amounts. `maskForPublic()` allow-lists the flag (default enabled), and public timeline cash flows use the same `flow()` convention as the app.

`Settings.gainColor` chooses gain/loss colors: absent or `green` means green gain, red loss; `red` swaps them. Money semantics use the `--gain` / `--loss` tokens in [design-tokens.css](app/src/design-tokens.css) (income, surpluses, refunds and price drops as gain; losses and price increases as loss), and `html[data-gain='red']` swaps them. The app root and the public page (through `maskForPublic`) set that attribute. Status colors (errors, done, overdue, danger actions) remain fixed red and green.

`currencyDecimals()` in [shared/format.ts](shared/format.ts) owns display precision: JPY, KRW, VND, IDR, CLP, HUF, TWD, PYG, MGA and BIF use no fractional digits; other currencies use two. `money()`, `flow()`, segmented `Amount` and chart ticks share this rule, including compact and explicit-precision formatting. Reports, image snapshots, reminders and formatted tool text inherit it without changing stored amounts or calculation precision. Currency-aware amount inputs reject newly entered fractional values for zero-decimal currencies with a translated message; historical values are preserved. Subscription list rows share content-sized category/payment/amount tracks and flexible name/date tracks, retaining the existing responsive column hiding.

Subscription details do not show the account (including phone numbers); it is edited only in the subscription editor. Notes appear in a final Notes panel at the bottom of the detail. Its eye toggle (shown on hover, always on touch screens and while masked) masks the note for the open sheet only; detail PNG export includes a visible note (without its expand link) and omits a masked one. For owner-organized shared plans, the current-period card shows the subscription period and the current member collection period ([collectionPeriod()](shared/carpool.ts)) side by side. The shared-plan detail repeats the same pair ([Periods.tsx](app/src/views/detail/Periods.tsx)) under its metric cards. The collection bar is drawn from aboard, non-exempt members' current periods and is hidden when they end on different days (the member timeline already shows each cadence); a prorated mid-period joiner that ends with the others still counts as the same cycle. The subscription detail then falls back to its single current-period bar, and the shared-plan detail shows only the subscription period. Other account editors and the public allow-list are unchanged.

Wallet payment cards in [Wallet.tsx](app/src/views/Wallet.tsx) simulate physical bank and SIM cards. Their material gradients, highlights and shadows are scoped exceptions to the plain-card presentation rules in [ui-basics.test.mjs](scripts/ui-basics.test.mjs). Pointer movement drives a reflection and tilt capped at four degrees; hover lifts three pixels. Sorting retains its independent `translate` timing, suppresses reflections during a drag and raises the picked-up card. Reduced motion removes tilt, lift and enlargement. Apple, Google Play and SIM faces retain light material with dark text across page themes; the fallback bank face remains neutral and dark. These effects do not change ledger state. Wallet detail sheets place edit, optional website and balance actions in the shared title toolbar before Close; icon buttons retain descriptive accessible labels and tooltips. Balance wallets omit the external recharge shortcut to distinguish ledger updates from visiting a provider.

A wallet balance is a calibration: `balance` as of `balanceAsOf`. `runwayFor()` in [shared/billing.ts](shared/billing.ts) subtracts charges dated after that day and treats the calibration day's own charges as included; a future `balanceAsOf` counts as today. Every balance write moves `balanceAsOf`: the editor through `editedBalance()`, top-ups and MCP directly. `Runway.spentSince` and `beforeShortfall` let reminders explain how the entered balance became the amount they quote, and a charge due today that the balance cannot cover is the shortfall that day. `current` always includes charges through today, because top-ups and calibrations build on it; a charge moved out of `current` would vanish once `balanceAsOf` moves. A top-up never saves an estimate that is not finite.

Ledger changes advance a monotonic `kv.rev` through database triggers in [0007_state_rev.sql](worker/migrations/0007_state_rev.sql), inside the same transaction as each write. Subscriptions, methods, dated FX and the `settings`, `people`, `prefs` and current `fx` keys participate, including imports, restores, MCP/assistant actions and scheduled FX writes. Authentication, token/config bookkeeping, notification logs and chat history do not change this revision because they are outside `/api/state`. Authenticated `GET /api/rev` reads only the revision; it and `/api/state` return `Cache-Control: no-store`. The public response omits the revision, and the service worker never caches `/api/rev`.

[Browser sync](shared/live-sync.ts) checks the revision every 30 seconds while visible, and immediately on focus, becoming visible or returning online (with a one-second throttle). Hidden tabs stop polling. A changed revision fetches a transactional state snapshot; successful local writes acknowledge their exact revision range so they do not cause an unnecessary full reload or hide intervening remote changes. A `BroadcastChannel` scoped to `BASE_PATH` announces successful writes to other tabs, which check immediately; polling remains the fallback. In-flight or overlapping local writes prevent stale snapshots from replacing local state. Recent preference edits have a five-second grace period, unsent preference keys remain protected, and remote preferences are mirrored into the local cache. Sync updates the store while open editors retain their own drafts. Offline checks fail quietly; 401 responses clear private state and return to login. This single-owner ledger uses polling rather than WebSockets or CRDTs: it needs neither new server-push infrastructure nor collaborative conflict merging.

Browser text search uses [search.ts](app/src/search.ts) and [use-search.ts](app/src/use-search.ts) across searchable pickers (including people and currencies), category icon groups, the command palette and subscription list. Literal names, symbols and codes remain case-insensitive substring matches. Only `zh-CN`, `zh-TW` and `zh-HK` lazily load the MIT-licensed `pinyin-pro` dictionary; simplified and traditional candidates gain full-pinyin, initial and mixed-syllable matching (`ü` also accepts `v`). Candidate indexes are cached with a bounded lifetime in browser memory and prepared independently of queries. A completed lazy load refreshes current results; a load failure retains literal search. This changes no stored state or API.

The editor's `NameField` combines local catalogue and App Store suggestions with no initial selection. Only an explicit arrow-key highlight enables Enter selection; pointer clicks still select and Escape closes the list. Composition events, `isComposing` and legacy key code 229 leave IME confirmation untouched. Unselected Enter retains the enclosing input/sheet behavior. The editor starts More options collapsed for every new subscription, including restored drafts. Existing subscriptions expand only when visible More fields contain data or explicit non-default settings; `editorMoreKeys()` and `editorMoreOpen()` in [more.ts](app/src/views/editor/more.ts) own the summary and initial state. Disclosure remains local to the open form.

Card and row subscription lists share `SubBadges`: owner sharing needs at least one recorded member, joined sharing uses the member role, upcoming status is shown only without a separate upcoming-phase badge, and proxy status comes from `ProxyBadge` (pending receivables).

Subscription filters in `List.tsx` default to all statuses, the current category route (or all categories), all payment methods and an empty search; Clear restores those values. Stopped subscriptions in both card and list views use their existing end-date display; estimated renewals avoided are not shown.

Monthly/day averages and timeline durations use `DAYS_PER_MONTH = 30.4375`. `durationLabel()` applies the history rule consistently: round days to months, display months once that rounds to at least one, otherwise days.

Horizontal-dominant wheel events inside the subscription timeline are always consumed, including the all-history range and before width measurement; vertical-dominant events remain available for page scrolling. The container contains horizontal overscroll and allows vertical touch scrolling.

The subscription timeline splits at each renewal returned by `chargesBetween()` (actual payment dates when recorded), price changes and introductory-price boundaries. It drops individual cuts that would create a piece narrower than its 22px capsule height. The three- and six-month windows merge adjacent renewal cuts within an unchanged-price run only when no visible piece can hold the price label; each unchanged-price run labels its first visible piece with enough room. This changes presentation only, preserving payment dates and billing calculations.

The subscription timeline in `app/src/views/Gantt.tsx` measures visible subscription names with the current font and label padding. `ganttLabelBounds()` in `shared/gantt.ts` limits the name column between its icon-only width and the longest name, capped at half the container width. Filtering, locale, font loading and container resizing refresh that measurement. Desktop and narrow-screen width preferences remain separate; rendering clamps saved widths without rewriting them. Narrow portrait screens show only named icons and suspend resizing, preserving the preference for landscape. Panning renders one extra viewport on each side and moves a translated layer during trackpad or drag gestures; React re-renders only when the gesture ends (then snapping to month anchors) or approaches the buffer edge, and position transitions are disabled while panning. Views that matter for re-render cost must compile under React Compiler; `scripts/react-compiler.test.mjs` fails on bailouts. The overview charge timeline keeps its full-length track but mounts icons, dots and month ticks only near the scrolled viewport. When icon packing would need overflow badges anywhere, it switches to one icon per charge day: the day's largest charge (by base-currency value) with a count badge when the day has several. Their tooltip (hover, focus, or a pinned dialog on click) lists that day's charges and total; single-charge days open the subscription directly, and sparse ledgers keep every icon.

The all-history window distinguishes ongoing service from the last drawn date: stopped subscriptions may retain future unused coverage without becoming ongoing. A stopped-only scope ends at the last drawn month's boundary and omits the today line, even when that month includes today; scopes with ongoing recurring phases retain today's margin. Lifetime-only points do not extend the range to today. Fixed zoom ranges keep the today line near the right edge with a short future margin (7 days for three months up to 45 days for three years); panning right still reveals later dates. Both service and unused segments retain a minimum 22px display width; this keeps short unused coverage behind the termination mark without altering dates, amounts or range calculations.

Report composition and annual-review payment summaries share `paymentMethodGroups()` in [shared/payment-groups.ts](shared/payment-groups.ts): groups use method IDs, and same-name methods append their recorded last four digits when available. This changes display only.

The main report page is scoped to one calendar year or to All, chosen in a toolbar dropdown (All, then next year down to the first ledger year; local state, default this year), with adjacent previous/next controls. The share button opens the review for the selection (All shares a cumulative review spanning first year to today) and is disabled only for next year; the review dialog has no selector of its own. All shows the cumulative hero (`allOutlook` total since the first charge, last 12 months, yearly average over elapsed days, peak year and peak month, cumulative monthly line), an all-time card (subscriptions used, stopped, summed carpool and proxy results per year), cash versus accrual aggregated by year through this month, the spending composition on cumulative spend, the subscription-tenure card (average served time of current and stopped subscriptions, stopped within 31 days, most subscriptions held at once, the six longest-served with their start month, and a monthly count of current subscriptions; `subscriptionTenure`, measured like the detail page's served time with gaps excluded, proxies excluded), and all cancellations. For a year, sections follow in order: the hero (that year's paid plus forecast, compared with last year's same period for this year and with the full previous year otherwise, and a cumulative January–December line, solid through today and dashed after), the year card, cash versus accrual for January–December, a daily heatmap switchable to isometric bars, the spending composition on that year's spend (every year), then for this year only monthly movement plus checkup row and the top-up/changelog footer. Past years show monthly movement (navigable only within that year, starting at December) beside the changelog filtered to that year; next year omits movement, changelog and cancellations. Prepaid value and the next-90-days metrics appear only for this year. Cash bars open `/calendar?month=YYYY-MM` for a selected year or `/calendar?year=YYYY` for All. [calendar-jump.ts](app/src/views/calendar-jump.ts) validates these parameters; Calendar consumes them once and selects a temporary month/year view without rewriting the saved `cal-mode` preference. The cancellations/terminations card is a summary: the selected year's unrefunded loss (my share, stop-date FX) plus counts of my cancellations and provider terminations stopped in that year, then one row per stop with an unrefunded loss (opens the subscription); the first five show and the rest sit behind a local More toggle. It omits hypothetical renewals avoided. Stops, starts and other lifecycle events are neutral everywhere in the report (no up/down arrow or red/green); only price changes and the month-total delta keep a direction. The checkup's duplicate warning keys on name, price and account, so deliberately separate accounts of one service are not flagged, and names a group once by its shared name. The report footer in `app/src/views/Report.tsx` uses a stretched two-column row above 680px. Its top-up card determines the height, with a 300px minimum when content is short. Size containment keeps the collapsed changelog from growing the row; a resize observer measures entry and year-heading heights to show only complete entries within the available space. The existing More action adds twelve entries and releases containment so the cards can grow. At 680px and below, both cards have natural heights and the log starts with eight entries. Disclosure is local component state and does not change the ledger or saved preferences.

Payment and stop forms default actual-card settlement currency to the selected payment account when it differs from the bill currency, otherwise to base currency; recorded settlements retain their currency. The default is shared by [settlementCurrencyOf()](shared/fx.ts).

## Billing and historical truth

Subscription detail history uses `detailHistoryEnd()` in `app/src/views/detail-data.ts` to bound stopped or paused charts, including each plan lane, instead of stretching them to today. Known stop/end dates remain authoritative; an undated stop uses the last recorded payment's calculated coverage only as a display boundary (or the last payment date when that coverage extends into the future). It never persists an inferred stop date. Undated stops show an explicit unknown-date label and omit precise duration/average-cost metrics. The Today marker appears only when today is inside the chart range; later actual payments remain visible even after a known service stop. Billing, accrued costs and stored subscription dates are unchanged by this display rule.

`Subscription` in `shared/types.ts` is the shared model. Charges and forecasts are derived by `shared/billing.ts`; `shared/phases.ts` supplies pure history-editing functions. Components and endpoints should call this logic rather than maintaining their own billing formulas.

Postpaid billing is the optional `billing: 'postpaid'` on a `Phase` and on the top-level `Subscription`. The top-level value mirrors the last phase, `phaseSubs()` applies each phase's own value, and a missing field means prepaid, so no migration is needed. Lifetime plans ignore it. In `shared/billing.ts`, a postpaid schedule does not charge the anchor. Each bill falls on the next cycle boundary, with lead days and offset applied, and is priced with `priceAt()` at its `serviceDate`, which is the previous boundary. `chargeServicePeriod()` returns that used period `[previous boundary, this boundary)`. End, stop, pause and a cancellation without an end all keep one final bill: the bill whose service period starts on or before the end or stop date, or before `pausedAt`. When an end date falls inside that final period, the bill is prorated to the days through the end. This covers a stop, which writes `end`, and a mid-period plan switch, which closes the old phase, so the old bill does not overlap the next phase. The final period that started before a pause is not prorated. A payment recorded after a stop counts when its period started on or before the stop. `billingPeriod()`, `stopSummary()` and `nonrenewalDate()` report no prepaid coverage for postpaid phases: `paid` is 0, `paidThrough` is the date asked about, there are no unused days, and there is no refund cap from prepayment. `stopBillingPeriod()` keeps future stops valid. A refund is capped by the latest bill on or before the refund date. Reports stay cash-based. Validation (`subError`, `shapeIssues`) rejects any other value, `maskForPublic()` keeps the field, and the MCP create, update and change-plan tools accept it through `billingSchema` in `shared/tool-schema.ts`.

A subscription may have multiple plan phases, including overlaps and gaps. Each phase can carry its own currency, price, cycle, payment method and adjustments. History-editing functions mirror the last phase into top-level fields for callers that use the current plan; the full phase history remains authoritative for past periods. Price changes and actual payment overrides are distinct inputs to charge calculation. A recorded payment may carry its own optional `methodId` for a one-off charge on another card; `chargeMethodId()` reads it before the phase's method, and history views, report composition, calendar, notifications, ICS and MCP charge rows use it. MCP `record_payment` sets it with `method` (null clears); `savePayment()` keeps a replaced charge's own `methodId` when the new payment omits the key. The payment sheet edits either that one charge or, through `setPhaseMethod()`, the whole phase (dropping per-charge overrides that then match). Deleting or merging a payment method migrates these per-charge references too: the web wallet (`DELETE /api/methods/:id?into=<id>` or `?clear=1`) and MCP `update_payment_method` action=delete share `deleteMethodData()` in [ledger-edit.ts](shared/ledger-edit.ts), which rewrites subscription, phase, per-charge and `funding` references plus `defaultMethodId` in one transaction. A referenced method cannot be deleted without a choice (HTTP 409 `in_use`, MCP requires `migrate_to`); only the web offers clearing, which leaves plans without a method, lets per-charge overrides fall back to their phase and drops `funding` splits that included the method (the remaining parts could no longer sum to the amount). A payment may instead carry `funding` (`[{methodId, amount}]`, at least two distinct methods, amounts in the subscription currency with the payment's sign, summing to `amount`; exclusive with `methodId` and `failed`), validated by `fundingError()` inside `subError()`. `chargeSources()` returns each source's share (one source, `chargeMethodId()`, when unsplit; `chargeMethodId()` itself reports the largest part of a split). Wallet runway, scope-report and year-review method composition and MCP `spending_stats group_by=method` allocate by these shares; charge tables stack the sources (amounts in the tooltip) and the payment sheet edits a split with one method + amount row per source. `savePayment()` keeps a replaced charge's split when neither `funding` nor `methodId` is supplied; method migration merges parts that land on the same method and collapses a single remaining part to `methodId`. The public mask keeps only `{methodId, amount}` per part; phases and payments themselves pass through allow-lists in [mask.ts](shared/mask.ts) (billing fields only, no notes or unknown fields). Wallet runway deducts recorded charges from their actual sources (per-charge method or funding share); future forecasts and monthly drain keep using the phase method. Ending a subscription early is recorded as a `stop` on the current phase (voluntary cancellation or provider termination) together with ordinary refund payments; `stopSummary()` derives the paid-through date, refund status and unused value that the timeline, reports and MCP tools display. The editor uses one Active / Trial / Paused / Stop control, with controlled stop fields from `StopPanel.tsx` and transient drafts in `shared/stop-form.ts`. Done validates and saves the entire draft; Cancel discards it, while closing the sheet retains an unsaved local draft. Existing stop details and recorded end dates can be corrected; full-record validation permits replacing an expired end date with a validated stop, while action-based MCP calls still reject already-ended subscriptions unless `set_status edit=true` corrects the existing stop through `editStop()` in `shared/stop-form.ts`, which fills the same stop form (omitted date, reason and refund keep the recorded values; a refund dated on the stop day moves with it; `refund: null` removes it) and applies it with `applyStopForm()`; an undated stop needs its real date, which `statusChangeError()` now accepts for undated records; refund fields edit the latest stop refund without replacing earlier payments. Returning to Active uses `reactivate()` and preserves recorded refunds; provider-terminated records cannot directly reactivate or change stop kind. The proxy detail stop dialog reuses the fields with its own Stop service confirmation; ordinary subscriptions stop only from the editor, and their detail header offers no stop or website action. MCP and assistant `set_status` retain their action and confirmation contracts, but cancel/terminate no longer default `at` to today when the subscription started or has payments before today; `at: null` records a stop on an unknown date via `stopUndated()` (status `cancelled`/`terminated` without `end` or `stop`, future planned phases dropped, no refund or reason). That state counts as ended, projects no further charges and is excluded from stop losses and cancellation savings rather than dated today; validation accepts `terminated` without a stop only when `end` is also absent, and such a record must be given a dated stop before resubscribing.

`savePayment()` treats an ordinary charge dated before the next due date as an early renewal when the previous period is settled: it records the settled service start as `Payment.serviceDate` and advances `nextDue` one cycle on the original billing anchor. The cash date never moves the service period, and `chargeServicePeriod()`, `billingPeriod()` and the bonus schedule read `serviceDate`. A charge paid before the next phase starts settles that phase's first period when the current phase has nothing left to bill. Deleting an early renewal shifts later early renewals back one period and restores `nextDue`, unless a later on-time renewal exists; a same-day edit keeps its `serviceDate`. When the previous period is unsettled the charge belongs to that period and nothing advances. Late payments keep the anchor, and refund, adjust, failed, postpaid, lifetime, trial, paused and stopped cases are unchanged. An extra charge between due dates must be recorded as `adjust`; payments saved before this rule keep their old `nextDue` until rewritten.

Payments saved before this rule keep their old `nextDue`. `settleLegacyEarly()` handles them at read time without rewriting storage: when the latest renewals have no `serviceDate`, each falls within half a cycle before its due date, no refund follows them and the period before them is settled, charges and billing periods treat them as early renewals; the next payment save or stop writes the result. A stopped or paused subscription is not recognized when the due date lies after the stop, so a stop persists the result first to keep its `paidThrough`. `PaymentSheet` previews the same outcome through `earlyRenewalEffect()` and lets the user switch the entry to an `adjust` when it is an extra charge.

Renewal rules are optional per-phase `chargeLeadDays` / `cancelLeadDays` fields (zero when absent). `renewalHistory` records effective-day edits, preserving earlier inferred charges and all actual payments; `reconcileRenewalRules()` enforces this on full-record API writes as well as MCP/assistant writes; full-record writes (`PUT /api/subscriptions/:id` and MCP `save_subscription`) share [prepareSubWrite()](shared/sub-write.ts), which also clears a removed member exit's refund and applies `validSub()`, `subRefsError()` and `statusChangeError()`. `subRefsError()` (also run by the MCP `commit()` path behind the narrower subscription tools) rejects payment-method ids and subscription/phase currencies (no positive FX rate) that the write newly introduces; values already present in the stored record pass, so records left with a dangling method id by older deletions or a currency missing from the current FX table remain editable. The same rule applies to field formats through `newShapeError()` in [billing.ts](shared/billing.ts): each phase's (and the top level's) start, price, currency, cycle, end (not before start, and not equal to the next phase's start, which would charge both phases that day; deliberate overlaps run at least one more day; switching or moving a start onto an earlier phase's end pulls that end back one day, stopping on a phase's start trims the earlier parallel phases likewise, and the switch panel's "keep until" default is the day before the old plan's next charge), `nextDue`, `intro` and `bonus`, a payment's optional `currency` (must equal its phase currency for every kind; the card's own currency belongs in `settled`), plus `trialEnd`, `pausedAt` and `tags` (an array of strings; `prepareSubWrite()` fills a missing list with `[]`); imports and backup restores do not run it. Consequently a web save that picks a currency absent from the stored FX table (for example a fresh install still on the fallback table) now fails like the MCP tools already did. First purchase and trial conversion keep their original date. Later charges subtract the lead from the original service-cycle boundary, retaining month-end anchors; `nextDue` remains a cash date. An edit never charges an already purchased boundary twice, and a newly advanced pending charge that would fall in the past becomes due on the effective day. Phase changes carry independent rules. `chargeServicePeriod()` keeps paid-through, accrual and prepaid value based on service coverage rather than cash timing. `renewalDates()` supplies next charge, rolling service expiry (the next service boundary) and cancellation deadline (cash date minus cancellation lead) to details and MCP. Nonrenewal defaults to the day before the next actual charge; after the cancellation deadline it includes the next purchased service period and the stop form warns that another charge remains due. Explicit earlier stop dates remain an owner correction.

The editor's More options includes Renewal rules, saved with Done. Name suggestions list the local service catalogue (`app/src/catalog.ts`, entries from optional packs in `app/src/catalog/`, icons served from `app/public/`; see [CONTRIBUTING](CONTRIBUTING.md#service-catalogue)) before App Store search results. New catalogue picks default Cloudflare Registrar to 30 days of advance charging and Apple App Store to one day of cancellation notice; App Store search/payment picks also supply the latter only for new records without an explicit value. Existing subscriptions and explicit zero settings are not overwritten by presets. Calendar, upcoming, reports, forecasts, wallet runway and ICS all use the shared cash schedule. Daily reminders reuse the existing reminder-day setting for both the actual charge and a separate cancellation deadline; disabling reminders disables both. ICS keeps cash events and adds a cancellation alarm using that same lead setting. Date calculations have day precision; a one-day notice is one calendar day, without an exact time-of-day guarantee.

Picking an App Store result in the editor also requests `/api/appstore/plans` ([worker/appstore.ts](worker/appstore.ts)). The Worker reads the store page's in-app purchase list and the same storefront's `lookup` currency; [shared/appstore-plans.ts](shared/appstore-plans.ts) parses names, prices and periods recognizable from plan names. Choosing a plan only prefills the unsaved form's amount, currency and recognized cycle. The store page is not an official API: a missing page, currency or unparsable price yields no plans rather than a zero amount, and the form stays manual. Name suggestions call `/api/appstore/search`; iTunes rate-limits by egress IP, and Cloudflare's shared egress is often limited, so a non-OK upstream response returns 502 (not an empty list) and the editor then repeats the same request directly from the browser to `itunes.apple.com` (CORS-enabled, no referrer), sending only the typed query and storefront. URL building, result mapping and the fallback decision (`searchWithFallback()`) live in [shared/appstore-search.ts](shared/appstore-search.ts) for both paths. Plan lookup has no browser fallback (the store page has no CORS), so it can be empty while the server is limited.

`pricePoints()` exposes an implicit initial price for phases without explicit history. `editPricePoint()` and `removePricePoint()` locate a point by phase start and original effective date; dates must be valid, unique and within that phase's inclusive service range (including overlaps). The earliest point cannot be deleted. Revisions sort the history and keep the phase price equal to its latest point, without changing other phases, billing anchors or actual payments. Deleting a later point extends the preceding price until the next change. Previously retained out-of-range points from start corrections may remain unchanged. Derived past estimated charges use the revised history; recorded payments remain authoritative. `affectedPriceCharges()` counts changed past estimates, excluding recorded and future charges. The editor asks before persisting when this count is nonzero. History shows phases and their price rows newest first in both editor and details; the editor writes valid inline date/amount edits and confirmed deletions into its form immediately. Invalid inline input stays visible and blocks Done until corrected or deleted; blur/Enter closes valid inline edits. Done asks once about affected estimates before saving, and the footer Cancel discards the form while other close actions retain the existing local-draft behavior. Deletion uses an inline `ConfirmButton`. MCP `change_price` supports add/edit/remove with the same rules and reports the affected count in previews and writes; `change_plan action=edit` can replace the phase's full price history, retaining the initial effective date, validating dates, sorting and deriving its latest price (clearing the entire history is rejected; move the initial date through `change_price`). Detail start/switch events use the initial price rather than the phase's latest price. Both retain existing write permissions and `dry_run` behavior; no stored schema changes are needed.

`movePhaseStart()` changes a phase's start key without reassigning its nested payments or rewriting actual payment, refund, stop, bonus or member-coverage dates. Starts remain strictly ordered and precede their effective end; explicit previous ends retain overlap/gap semantics. The first start also updates `Subscription.start`. Initial price points follow the new start; when crossing a later price change, the dated history is retained and the effective price is pinned at the new start. The optional `billingStart` field retains the original recurring anchor independently of `nextDue`, including month-end alignment and prepaid future renewal dates; moving a recurring start earlier now infers the newly added cycles before that anchor using the original day-of-month and rules, while recorded payments override same-day estimates and recorded-history gaps and later renewal dates remain unchanged; old records fall back to `start`, JSON backups preserve it, and public masking retains this non-identifying billing date; inferred lifetime purchases become explicit payments. Paid-period calculation includes payments and billing anchors preceding a corrected service start, preserving stop/refund validation. An inferred sharing anchor and sharing start are pinned before moving the first phase. Editing an out-of-coverage payment without changing its date keeps its original phase and currency. The editor places History before More options at the bottom of the form. More options starts collapsed on every open when its visible fields are empty, and expanded when any contains data (including icon URLs); toggling it is local to the open form. The editor offers one start-date input per phase in History (the top input remains for new subscriptions), with confirmation before existing payments newly fall outside service coverage. MCP start corrections report the same payments as `payments_outside_service_period` in both previews and writes without blocking them. These corrections (`change_plan action=edit set.start`, `update_subscription set.start` for single-phase records) call the same `movePhaseStart()`, so the billing anchor and future charge dates stay unchanged and previews show the unchanged `next_charges`; an explicit `shift_billing: true` instead clears the anchor so estimated charges move with the start (and a lifetime purchase date moves with it). Other MCP phase tools create, confirm or drop phases; permissions and preview behavior are unchanged.

Stopping a paused subscription on or after its pause date records `Stop.pausedAt`; lapsing one that way becomes the same stop, since no paid period remains to wait for. `pausedFromOf()` in [shared/billing.ts](shared/billing.ts) makes billing, member dues and contribution metrics honor it, so charges skipped during the pause stay absent, the entered stop date is kept, the paid period ends before the pause, and a later resume keeps it on the old phase. Restoring a stopped subscription clears it. Stops stored before this change are not rewritten. When a dated pause ends, `closePause` in `prepareSubWrite` appends it to optional `Subscription.pauses` (`{from, to}`, `to` exclusive) without touching phases, prices or payments: projected charges skip the span, the next charge is the next natural charge day, recorded payments stay, a postpaid period starting inside the span bills only the days after resume, and `billingPeriod` starts a period whose charge was skipped at the resume day with `paid: 0` (refunds there are capped by the last real charge). Writes to an existing record cannot change the stored list. Member dues, lifecycle events, timelines and served days do not read it yet. `stopLosses()` in `shared/metrics.ts` aggregates unrefunded unused service per stopped phase, excluding proxy payments and applying my share and stop-date FX. It uses `stopSummary()` with refunds known as of the report date; prorated full refunds have zero loss. The report and MCP `get_insights` (`stop_losses`) expose all history, while `yearReview().stopLoss` filters by stop date in the selected year. Prepaid unused totals and health-check reminders reuse this calculation; losses are separate from the hypothetical renewals avoided in `cancelSavings()`, which remains available to other views and MCP `get_insights` (`cancel_savings`). If both dated and current FX are unavailable, loss rows retain original amounts and mark the aggregate incomplete (`NaN` internally, `null` in MCP base amounts/totals), rather than reporting zero.

Optional `Subscription.transfers` ([shared/transfers.ts](shared/transfers.ts)) records owner-to-owner cash for a second-hand service: `buy` (Bought / 买入) is what was paid to the previous owner, `sell` (Sold / 卖出) what was received when handing it on (`{kind, date, amount > 0, currency, note?}`, any currency, actual cash rather than residual value). They are not provider charges: MRR, forecasts, wallet runway, refunds, charge lists/counts and scope-report composition ignore them. `netCost()` gives lifetime net cost = service charges + buys − sells at each transfer date's FX (missing FX yields `NaN`/incomplete, never zero), averaged over `holdingPeriod()`: from the earliest buy when it precedes `start`, to the last sell (exclusive) when the latest transfer is a sell, otherwise today, counting served days without gaps. Subscription details then label the KPIs held / net cost (net gain when negative) with the service-charge count, and list the transfers once in their own year-grouped table (outflow negative, inflow positive under `signedAmounts`), plus amount-free event markers. `transferredStop()` marks a stopped phase whose paid service went with a sell dated between the phase start and its paid-through date: `stopLosses()`, the detail outcome card and the timeline's unused segment then report no paid-but-unused loss. `yearReview()` and `monthReport()` headline/six-month cash include transfers dated up to today; charge counts, composition, top and upcoming rows do not. `subError()` validates transfers for every write path (full `PUT`, imports/restores, MCP). The editor's More options edits them through `TransferSheet` as part of the form draft saved with Done; details can add/edit them directly. MCP `record_transfer` adds, replaces (`replace={date,index}`) or deletes (`delete={date,index}`) one with `dry_run`, and `get_subscription` returns `transfers`, `net_cost` and per-phase `transferred_on`. Proxy subscriptions cannot record transfers. The JSON field needs no SQL migration and round-trips through backups; `maskForPublic()` does not allow-list it, so public totals omit transfers.

Optional `Subscription.meters` and `Subscription.readings` ([shared/meters.ts](shared/meters.ts)) hold user-defined business data (electricity, mileage, traffic…): meters are `{id, name, unit, kind?}` (`kind: 'reading'` is a cumulative counter, omitted = usage per period) and readings are dated `{id, date, values: {meterId: number}, note?}`, stored apart from payments and never billed. Derived values are computed on read and never stored: a usage meter's period usage is its value; a reading meter's usage is the difference from the previous reading that has that meter (none for the first one or when the counter goes backwards); a usage meter's reading dated before the subscription start belongs to no charge period, so it carries no usage and is left out of totals, matching the charge records. Quantities show the meter's most precise recorded decimals (at most three, `meterDecimals()`). Unit price = actual charges in `(previous reading date, date]` from `chargesBetween()` (projected and failed excluded, original currency; none for mixed currencies) ÷ usage, absent when usage is 0 or missing or there were no charges. `meterError()` runs inside `subError()` for web PUT, MCP and imports (unique ids, non-empty names, valid dates, finite values that reference defined meters); `removeMeter()` / `replaceMeters()` strip a deleted meter's values and drop readings left empty. `maskForPublic` copies neither field. Detail renders them in [detail/Meters.tsx](app/src/views/detail/Meters.tsx) right below the fee timeline, sharing its date axis and range (`timelineAxis()` in [detail/ChargeTimeline.tsx](app/src/views/detail/ChargeTimeline.tsx)); clicking a bar edits that reading. Its meter switch is Detail state that also selects the usage row of the top metrics (`usageMetrics()`). The charge records add a column with the first meter's usage per charge: `usageWithin()` sums readings dated inside the charge's service period from `chargeServicePeriod()` (failed charges and refunds show none). The charge sheet ([PaymentSheet.tsx](app/src/views/PaymentSheet.tsx)) has one field per meter for a regular charge: `periodReading()` picks, per meter, the latest reading inside that service period that carries it (a meter with several readings there is read-only, showing the summed usage), and on save `setPeriodValues()` writes only the edited meters in the same `saveSub()`, into that reading, else any reading of the period, else a new one dated at period end (or today while the period is open), and drops a reading left with no values; deleting the charge leaves readings alone. Postpaid period bills are placed by the period they settle, not the cash date (a bill paid off the boundary settles the period that ended most recently before it, skipping a period whose due date already has another regular payment, so a late bill paid after an on-time one goes to the earlier period): `chargeDay()` (period end) groups the charge records by year and picks the timeline range, both charts draw postpaid fee bars and usage bars at the middle of their period (`barDay()`, `midDay()`; a projected bill whose midpoint has passed sits at period end, right of today) so a bill and its usage share a month, and for postpaid subscriptions month tick labels sit on the 15th so a mid-month bar falls on its own label (`ChargeBars` `midMonth`), the records' date column shows the period (header Period when every regular row is postpaid, cash date in the row tooltip) and the tip titles the period with a Paid row; calendar, cash flow and report cash totals keep the cash date. Both charts share one charge tip ([ChargeTip.tsx](app/src/views/detail/ChargeTip.tsx)): service period, amount, converted amount only when the currency differs from the chart's, usage with average price, and payment method; a usage bar shows the charge whose service period contains its reading, or only the date and usage before it is billed. MCP `set_meters` / `add_readings` edit them with deterministic new ids so assistant previews and confirmed writes match, and `get_subscription.meters` returns the derived rows.

A meter may instead carry `link: {subId, meterId}`, reading a meter owned by another subscription (the same mileage on car insurance and a charger). It stores no values: `meterError()` rejects readings on a linked meter id, and values are written only on the owner. `meterView()` builds a read-only copy for every derived figure: the source's name, unit and kind plus its readings with their original ids, trimmed to the days this subscription actually served: per-phase ranges, so gaps between phases and days after a pause or stop are out, and a parallel phase counts while any phase covers it. A cumulative meter restarts at each stretch of service, using the reading just before it as base when that is at most 31 days earlier and otherwise the first reading inside it, marked `base` on the view's copy only; differences across unserved days never count as usage. Editors save the raw subscription, never the view; [detail/Meters.tsx](app/src/views/detail/Meters.tsx) edits one subscription per save with `writeReading()` / `removeReading()`, which keep other meters' values on the same reading. Links are one level deep. `meterLinkError()` compares the ledger before and after every web PUT, web DELETE, MCP write, MCP delete and `/api/import`, and rejects only references that write breaks, so deleting a source or a source meter is refused while something links it and unrelated edits to an already dangling record still save. Backup restore is exempt because a backup must stay restorable. Validation and commit are not one transaction, so concurrent writes can leave a dangling link; no values are lost, the web page says the source is gone and `get_subscription` returns `source_missing: true` with null totals instead of zero. Viewing a subscription's own meter overlays its first resolved linked meter as a line with an independent scale and no second axis. When one charge's service period holds at least two usage records, the usage metric's average price comes from `spreadUnitPrice()`: actual charges, refunds and adjustments prorated over the recorded time, divided by the usage recorded inside billed service periods (the as-of note shows the last such record; a usage meter whose recording starts mid-life starts from the period holding its first record; mixed currencies or a fully refunded charge give no price). MCP `latest_unit_price` uses the same figure, and per-reading `unit_price` is then null. The charge tip omits an average price until records cover the period from start to end, and whenever the period holds a refund or adjustment (`chargeOpen()`), and yearly totals count each reading once across parallel phases (`chargesUsage()`). Public responses carry neither meters nor links.

## Persistence and migration

`worker/store.ts` is the persistence layer. The database stores:

| Storage                                                     | Contents                                                                                                                                                                                                  |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `subscriptions`, `methods`                                  | JSON records keyed by ID, plus update timestamps. Subscription JSON `updatedAt` is stamped only by `worker/store.ts` on every store write (imports and restores keep the stored value); nothing reads it. |
| `kv`                                                        | Settings, the people roster, preferences, current FX and credential/configuration records. This SQL table is not Cloudflare KV.                                                                           |
| `fx_daily`                                                  | Exchange rates and source by date.                                                                                                                                                                        |
| `sessions`, `passkeys`, `auth_challenges`, `login_attempts` | Authentication and device state.                                                                                                                                                                          |
| `notify_log`                                                | Delivery records with deduplication keys.                                                                                                                                                                 |
| `chats`                                                     | Stored assistant conversations.                                                                                                                                                                           |

SQL files in `worker/migrations/` define schema history. `scripts/migrations.mjs` generates `worker/migrations.gen.ts` during `npm run build`; `ensureMigrated()` applies missing migrations and records them in `d1_migrations`. The generator uses Wrangler's SQLite-aware statement splitter so multiline trigger bodies stay intact. Wrangler's migration command uses the same tracking table. Add migrations rather than editing already-applied ones.

Renewal fields use the existing JSON records and require no SQL migration or backup-version bump. `migrateRenewalRules()` is an idempotent, read-only compatibility conversion used by state reads, charge derivation, public masking and backup import. A valid positive gap between a legacy `expires` and its preceding scheduled charge becomes advance-charge days; `renewalOffsetDays` preserves the original cash anchor and expiry display while future service boundaries roll forward. Stopped records and lifetime purchases keep their existing paid-through contract; invalid or nonpositive gaps fall back to zero rather than inventing a lead. Historical price points continue to select the cash-date price. The deprecated `expires` value is retained for older consumers, but the detail summary uses derived expiry. A normal subsequent save persists optional fields; reads and MCP previews do not write them.

Receivables changed shape without a SQL migration. [shared/receivables-legacy.ts](shared/receivables-legacy.ts) `migrateReceivables()` converts legacy members (`paidUntil` plus coverage-based `payments`) and proxy `entries` once: it first pins the legacy-inferred `collectFrom`, records a `restarts` date wherever an explicit coverage start or the day after `paidUntil` is not a derived period boundary (so next collection dates and dues stay as before), assigns each payment to the periods starting within its coverage (or an overlapping/original key, never dropping money), turns remaining periods up to `paidUntil` into one opening settlement, and maps proxy entries to charges (exact date, else within 15 days except for batches), merging batches into one receipt and keeping charged overrides as `Proxy.charged`. It returns already-converted records unchanged. `loadState()` always converts in memory and, outside the no-write MCP/assistant reads, writes changed subscriptions back before linking people; imported or restored backups convert on the next load.

People remain in the existing JSON roster, including optional image data URLs. Avatars require no SQL migration; each image is square, at most 128px and 64 KiB, with no remote URL, animation or metadata chunks. All roster write paths enforce a 1,800,000-byte UTF-8 budget, leaving room below D1’s single-value/row limit on both Cloudflare and Docker. Oversized/invalid images or rosters fail before persistence; existing data is retained.

Backup versioning and compatibility live in `worker/backup.ts`. Exports include subscriptions, methods, people, settings and FX history; they do not recreate login sessions, MCP access tokens or delivery logs on a new installation. Settings may contain notification and other credentials, so backup files are sensitive. A JSON export is not a copy of the whole SQLite database. Optional person avatars round-trip in v3 backups; older backups without avatars or a roster still load. Import validates the roster before replacing ledger data. Restore replaces subscriptions, methods, roster, settings and current FX and merges dated FX in one D1 batch (one transaction; D1 counts a batch as one query and sets no statement-count limit), so a failing row leaves the existing ledger unchanged. People-roster writes with their linked subscriptions likewise use a single batch. CSV is a narrower interchange format.

The ordinary data-import entry accepts existing CSV exports plus offline subscription databases and ZIP backups. `app/src/import-file.ts` lazily loads SQLite/WASM and `shared/import-backup.ts` reads only whitelisted business columns in the browser, never restoring the source database or uploading its credentials. File/unpacked-size and row limits, database shape checks, and pending-WAL rejection fail visibly. `shared/import-ledger.ts` normalizes the records for the preview: multi-account backups require selecting one account; ambiguous currency symbols require explicit correction; invalid amounts, cycles, currencies or start dates block confirmation unless corrected or excluded (this includes Calends and iOS Subscriptions CSV, whose comma decimals, unknown cycles, blank currencies and unreadable start dates are no longer guessed as other values; a blank start still defaults to today with a note); an unrecognized next-payment or end date (which has no correction field) is not imported and its original value is kept in the notes. A payment-method name reuses an existing or already-created wallet of the same name, preferring the same currency, instead of creating same-name wallets. Same-name records keep independent IDs; extra source categories become tags and payer labels remain notes rather than inferred receivables. Inactive/manual-renewal records import paused. Images are limited to small raster logos: PNG/JPEG/WebP up to 64 KiB become `data:image` icons; [shared/icon.ts](shared/icon.ts) is the single icon classification used by the app, public page, ICS and notifications, so embedded images render as images in the UI and are never emitted as text in calendar summaries or handed to notification channels (which fall back to the site favicon). Only the normalized subscriptions and referenced payment methods use the existing authenticated import API after confirmation; the Calends JSON restore flow remains separate.

Only external sources (offline backups and foreign CSV) set `estimateFrom`; Calends and iOS Subscriptions CSV exports carry complete billing rules and keep inferring history exactly as before. Imported subscription JSON carries optional `estimateFrom`: service start and next-payment dates remain intact, but `chargesBetween()` does not infer charges before the import boundary. Explicit recorded payments before that date still count, including after a plan is split into phases. The boundary only affects spending: `billingPeriod()` ignores it, so the current paid period, refund cap, prorated refunds and unused days stay correct for an imported plan before its first recorded charge. Details disclose the incomplete earlier history and MCP returns the boundary/completeness alongside totals; public masking retains this non-identifying cutoff so private/public calculations agree. Existing records without the field retain their billing behavior; JSON backup/restore preserves it without a SQL migration.

## Authentication, public data and AI

`worker/auth.ts` owns password setup, salted password hashes, passkey challenges, session cookies, device revocation and renaming. Settings → Security renames a passkey or signed-in device in place (`PATCH /api/auth/passkey/:id`, `PATCH /api/auth/sessions/:id`; trimmed, at most 40 code points; a non-string name is 400 and a revoked or deleted target is 404). A passkey name cannot be empty; clearing a device name stores `NULL` in `sessions.name`, and the device is shown by browser and OS again. `SETUP_TOKEN` protects the first owner-password setup. Login offers cancellable WebAuthn conditional autofill alongside password and explicit passkey login, using independent five-minute challenges; expired autofill challenges are retried silently. The explicit button requests options with `?mode=button`, which lists the bound credential IDs in `allowCredentials` (without transport hints, which can filter out third-party password managers) so the platform and password managers look only for those; conditional autofill keeps the list empty. The login form's account field is a fixed `username` input with the value `owner@<hostname>`, visually hidden (clipped, not `display:none`), out of the tab order and hidden from assistive technology: the server ignores it, but it stays a non-read-only field in the form because read-only or undisplayed fields are skipped by Safari and password managers, so the account and password would not be saved together. When the server rejects a credential picked from autofill (not bound, failed verification, throttled), the login page shows the reason (the not-bound and failed-verification messages tell the owner to sign in with the password and add the passkey again under Settings → Security) and re-arms autofill; failures before a pick stay silent. An unknown credential returns `PASSKEY_NOT_BOUND`, and the browser then calls `PublicKeyCredential.signalUnknownCredential` where supported so the password manager can hide or delete it. The passkey relying party (RP ID and expected origin) comes from `SITE_URL` when set, otherwise from the request URL, so a Docker instance behind an HTTPS proxy matches the browser origin even though wrangler sees plain http; verification failures are logged server-side with their reason while the client gets a generic error. New passkeys use `owner@<hostname>` as the form account identifier and a display name combining the configured name (or Calends) with the hostname; existing credentials remain valid. Failed password, setup-token and passkey logins are limited per visitor IP (six failures per fifteen minutes): Cloudflare supplies `cf-connecting-ip` and the Docker front listener always overwrites it, so the Worker reads no other header. When no IP is available (for example a bare `wrangler dev`), failures are not counted in a shared bucket, which would let anyone lock out the owner; each failure is delayed instead. Authenticated browser APIs use sessions; an ICS URL contains its own private feed token, compared in constant time before the ledger is loaded (read-only, so feed requests never write).

The signed-in image relay `/api/img` (same-origin icons for canvas snapshots) only fetches public `https` addresses through [worker/url-guard.ts](worker/url-guard.ts): loopback, private, link-local, CGNAT, metadata and reserved literals (including normalized numeric forms, IPv6 multicast, and IPv4 embedded through IPv4-mapped, IPv4-compatible, NAT64 `64:ff9b::/96` / `64:ff9b:1::/48` and 6to4 `2002::/16` addresses; unparsable IPv6 literals are refused) are refused, and redirects are followed manually with each hop rechecked, so it cannot probe the host's internal network. Owner-configured endpoints (notification webhooks, the assistant base URL) are intentionally not restricted.

`worker/ai/mcp.ts` provides stateless Streamable HTTP at `/mcp`, using JSON-RPC responses rather than a persistent server-push stream. A JSON-RPC batch runs its calls sequentially in array order, so later calls see earlier writes. `/mcp` is a service endpoint; opening it in a browser redirects to the app's AI access page at `/connect`. Only token hashes are stored. The token list (`mcpTokens`) is written only by the AI-access management API; authentication records last use in a separate `mcpTokenUse` map with a single-statement JSON update, so a concurrent request cannot resurrect a revoked token or drop a new one. Read tokens cannot call write tools; the AI-access setting can disable the endpoint. The [connection page](app/src/views/Ai.tsx) starts with every client collapsed. Client buttons toggle inline setup steps without persisting selection. A newly created raw token is available only in its creation sheet, where setup snippets include it; closing the sheet discards it. Main-page snippets always use a placeholder.

`create_subscription` and `update_subscription.set` accept optional camelCase `chargeLeadDays` and `cancelLeadDays` (integer days, 0–3660). `create_subscription` also accepts `status` `cancelled` (with `end` as the last service day, or undated) and `terminated` (with `end` it builds a provider stop through `stopSubscription()`, otherwise undated); `method: null` skips the default payment method; payment items accept `kind`, `method`, `settled` and `funding`. `create_subscription.icon` and `update_subscription.set.icon` share `iconInput()` in [shared/icon.ts](shared/icon.ts): an http(s) URL, a site path, a png/jpeg/webp data image within the import size limit, or one emoji / short symbol (up to four graphemes); empty or null clears it, and any other value is rejected instead of silently dropped. `save_subscription` creates or replaces one complete record (phases, payments, stop, status) through the same `prepareSubWrite()` as the web editor's PUT, plus MCP category resolution (payment-method and currency checks are part of `prepareSubWrite()`) and the same-name duplicate guard for new records; it does not mirror top-level fields from phases. Its preview adds field-level `changes` against the stored record and `computed` before/after (status, next/last charge, spent to date, stop summary). It is a destructive-hinted write; read tokens cannot call it and the assistant confirms it like other writes. The full-record JSON schema in `shared/subscription-schema.ts` describes phases, per-phase payments, free intervals, stop details, sharing and transfers, including an early-renewal example. Known fields are checked with precise input paths; legacy extension fields and optional null removal remain supported. Permission scopes and dry-run behavior remain in place. Subscription read rows include `next_charge`, `service_expires` and `cancel_by`; `get_subscription.expires` is the derived rolling service expiry and its `record` retains editable source fields.

`save_person` accepts `avatar_base64` with `mime` (`image/png` or `image/webp`) for a prepared thumbnail, or `avatar=null` to remove it. There is no remote image fetch; unknown `avatar_url` inputs, including HTTPS, are rejected. `list_people` and person mutation summaries expose `has_avatar` without inline image data. Each shared-plan entry in `list_people.in` includes its own `account` (null when absent); proxy entries have no account. `save_share_member.account` edits or clears only that membership, retaining write permissions and preview behavior. `save_share_member` (an unlinked member without `person`) and `set_proxy` (`for_name` without `person`) apply the same `personLink()`: they link a matching roster person or create one in the same transaction as the subscription; previews return `created_person` and `person_notice` (also shown on assistant cards) without writing, and the derived id keeps preview and confirmation aligned. `person: null` keeps the member or recipient unlinked. Avatar mutations retain the same scopes, preview overlay and assistant confirmation path.

The ordered catalogue in `worker/ai/mcp-tools.ts` composes the read, subscription, sharing and ledger handlers listed in [AI access](worker/ai/README.md). Shared resolution and the single write pipeline live in `tool-kit.ts`; output formatting lives in `tool-views.ts`. Both MCP and the in-app assistant reuse that catalogue. Write tools support `dry_run`, which previews the proposed ledger change without saving it. External MCP clients may execute writes with a write-scoped token; confirmation is their responsibility. The normal in-app assistant forces write calls into proposals, then invokes the tool again after confirmation through its apply endpoint. Do not conflate those two flows.

MCP initialization instructions and `get_settings.connection` expose the configured ledger name/site, local date, time zone, base currency, caller scope and available tool names without token values, hashes or channel credentials. Read tokens see only read tools; the assistant identifies its draft/confirmation flow separately. Connection inspection does not add a tool or change permissions. Subscription list rows include the private login account and search includes account, region and payment method. Ambiguous names return account/region/payment context before the caller selects an ID. Creating same-name/same-start subscriptions with explicitly different accounts is allowed; matching/unknown accounts still require explicit `force` for a possible duplicate. Same-name services alone never justify merging or cancelling them.

The catalogue contains 36 tools (listed in [AI access](worker/ai/README.md#tools)). Ledger editing includes wallet creation/full edits/deletion and top-up revisions via `update_payment_method`, category and person registries via `save_category` / `save_person`, proxy relationships via `set_proxy`, and non-secret settings/preferences via `get_settings` / `update_settings`. Settings writes (`PUT /api/settings` and `update_settings`) share `checkSettings()`: base/collection currency, default payment method, time zone, language, startup route and avatar are validated only when they change, and only newly added `publicHidden` ids must exist. `pruneSettingsRefs()` drops `publicHidden` ids and a `defaultMethodId` that no longer resolve: `loadState()` applies it in memory only (so reads, `create_subscription` defaults and MCP previews never see them, without a data migration) and both settings writes persist the cleaned values. Subscription category references must resolve uniquely against the effective category list (including historical names); unknown names require explicit creation and ambiguous names fail. Explicit category creation and the subscription write share one transaction, and previews expose the proposed category without saving; see [category tool behavior](worker/ai/README.md#tools). Multi-entity migrations use one transaction in `saveLedgerEdit`; reference and field-whitelist rules live in `shared/ledger-edit.ts`. Editing/deleting recorded top-ups preserves the calibrated balance unless explicitly changed. Removing a receipt or waiver reopens its periods.

All advertised input schemas are enforced at runtime on both MCP and assistant callers, including `pattern`, `minItems`/`maxItems`, enums, bounds and date formats ([shared/tool-schema.ts](shared/tool-schema.ts)). The assistant receives the entire same catalogue, always forces write calls into drafts and keeps wallet/person/category/settings/preferences in its per-turn overlay alongside subscription drafts. Creation IDs are fixed in confirmation arguments. In the browser, a reply stream that closes without its `done` event, or one still marked streaming when a saved chat is reopened, is shown as interrupted; only the current conversation offers retry, while archived conversations have no retry handler. Leaving the assistant page aborts the stream. Retrying a failed confirmation first refreshes the ledger and treats a `create_subscription` whose fixed ID already exists as unverified, preventing a second create. Unknown or server-failed writes are also unverified; dependent confirmations stop on uncertainty. Confirmation cards expose before/after and reference summaries; apply re-runs validation against current data. MCP state reads skip implicit legacy people migration, preserving no-write previews. The connection page dynamically lists the catalogue with localized titles and code names, grouped by read/write permission and ordered by domain; tools from unrecognized domains remain visible at the end of their group.

Assistant execution has a bounded 12-round tool budget. Failed previews do not enter the successful-draft deduplication set and may retry after dependencies are drafted. A successful same-tool/target operation can resolve its earlier error. The final SSE `done.outcome` separates `complete`, `partial` (unresolved tool errors) and `limit`; a tool-free closing request is attempted at the limit, with a deterministic limit outcome even if the provider cannot summarize. The UI suppresses an untrusted final completion claim on partial/limited turns and keeps successful drafts available for individual review. Batch confirmation stops at the first failed or unverified save and cannot automatically continue past an uncertain result.

Confirmation re-previews current data, pins creation and receipt/waiver IDs/defaults, saves, then re-reads persisted business state. `shared/assistant-result.ts` checks intended entity and setting changes while ignoring metadata timestamps and unrelated concurrent edits. The apply response adds `verification.status=verified|unverified` and mismatching entity/setting paths. Read-back failure after commit returns an unverified result, not a retryable save failure. Network/5xx ambiguity is likewise shown without a blind repeat button; a page refresh failure does not relabel an already-saved proposal as unsaved. This verifies persistence, not semantic equivalence to arbitrary natural-language intent; users still review the proposed dates and amounts.

AI ledger tools deliberately exclude authentication/passwords/Passkeys, sessions/session limits, MCP tokens/AI access controls, private ICS tokens, provider keys/configuration, backups/import/export/restore/reset/migration, whole-ledger deletion and outbound notification configuration/addresses/secrets. Settings tools allow only existing channel enable switches and sanitized channel metadata. FX refresh/backfill, notification delivery/tests and chat archival are operational actions outside the ledger-tool boundary. Public responses still pass through `maskForPublic`.

The sharing tools expose the same first-period alignment and independent subsequent collection rules: `set_share` accepts optional `collect_from` and returns the effective anchor; `save_share_member` accepts `leave_refund` (positive actual amount with date defaulting to `left`, currency defaulting to the suggestion; `null` clears), and previews return `suggested_refund` with original-currency parts plus `unused_days`. Member query/save summaries expose `leave_refund`; omitting it preserves the settlement, and `left=null` clears it. It also accepts optional `joined`, `first_period`, `first_amount`, `collect_day` (new members) and `fee_from` (fee changes default to today and preserve the previous baseline), returning a member summary with inclusive `first_collection` coverage and fee, the anchor, paid-through and next collection date in previews and saves. `record_receivable` works per period for both kinds: `action=record` (default) covers `periods` (period keys from `get_subscription`, may skip earlier owed ones or be future) or the `count` earliest unsettled periods (default 1), with `amount` defaulting to their total due converted to the requested currency at the receipt date; an explicit amount is the actual receipt, split across the periods by their dues. `waive`, `update` / `delete` (by receipt or waiver `id`) and proxy-only `charged` (one charge date's actual card charge; `null` clears) complete the set. A period can be settled by only one record. The response includes the record (`after`) and, for members, the updated summary; the assistant pins the previewed periods, amount, currency and date into the confirmation. `save_share_member.paid_until` sets the opening settlement. `get_subscription` lists every member's and proxy's `periods` with status, due and record ids, plus `unmatched_records`. `get_carpool` exposes the overall and per-member anchor, billing months, paid-through, `next_collection_date` (earliest unsettled period, possibly overdue), `pending_amount` (total of owed periods as of today, zero if none) and `is_first_period` (whether that period is the first). The assistant uses these results for collection dates and dues instead of calculating them itself. Legacy `record_receivable` arguments (`index`, `entry`, `from`/`until` and `paid_until`) are no longer accepted; external clients must use period selection and record ids. Tool names, write permissions and preview behavior are unchanged.

## Deployment and background work

Personal deployment files use `CALENDS_LOCAL` (absolute or relative to the repository root, default `local/`), resolved by [scripts/local-config.mjs](scripts/local-config.mjs). [scripts/wrangler.mjs](scripts/wrangler.mjs) automatically selects its `wrangler.jsonc` when present unless `--config`/`-c` is explicit; local commands default to `<repo>/.wrangler/state` independently of that directory. [app/vite.config.ts](app/vite.config.ts) serves its `public/` overrides in development and copies them into `dist` during builds. See [self-hosting](docs/self-hosting.md#personal-cloudflare-configuration) for external configuration paths and commands.

Cloudflare runs the Worker with D1, bundled static assets and Cron Triggers. Docker runs the same Worker in one Node process, without Wrangler or workerd, because the `wrangler dev` chain grows without bound and keeps esbuild alive. `npm run build:docker` bundles [docker/entrypoint.mjs](docker/entrypoint.mjs) and the Worker into a single file, so the image ships no `node_modules`. The entrypoint forces `TZ=UTC` (Workers semantics), refuses to start if the expected database is missing while other `.sqlite` files or the setup-token file exist (a replaced empty volume, or `SETUP_TOKEN` set with no token file, cannot be told apart from a fresh install), prepares the setup token, runs `ensureMigrated` and fires the scheduled handler every 15 minutes in-process. It drains `waitUntil` work and closes the database on SIGTERM. [docker/d1.mjs](docker/d1.mjs) implements the D1 subset the Worker uses on `node:sqlite`, with `batch` as one transaction. [docker/assets.mjs](docker/assets.mjs) replaces the assets binding, including SPA fallback; hashed `/assets/` files are immutable. [docker/front.mjs](docker/front.mjs) serves the published port: `/healthz` checks the database without entering the Worker, responses are gzipped, client `CF-Connecting-IP` is replaced by the visitor address from [docker/client-ip.mjs](docker/client-ip.mjs) (the socket address unless it is local, private, Cloudflare or listed in `TRUST_PROXY`; then the first untrusted `X-Forwarded-For` entry from the right, and Cloudflare ranges are not trusted on requests marked `CF-Worker`), and request bodies are capped (`maxBodyFor`: 64 KB for login routes, which parse before authenticating; 20 MB for backup, import and assistant chat, which authenticate first; 4 MB otherwise). A declared oversized body gets 413; a chunked one is cut off at the limit and fails as an unreadable body.

Docker memory is bounded by `NODE_OPTIONS=--max-old-space-size=192` in the image and `mem_limit` in Compose. The database stays at Miniflare's old path under `/data/v3/d1/miniflare-D1DatabaseObject/`, so upgrades need no data migration and an older wrangler-based image can read the same volume. Docker does not require a Cloudflare account.

Both targets use the scheduled handler in `worker/index.ts`: every run checks reminders against each owner's local send time and retries failed deliveries; the run at the top of each UTC hour also handles FX maintenance. Delivery deduplication and retry decisions belong to `worker/notify.ts`, not a browser timer. A send claims its deduplication key with a ten-minute lease (`SEND_LEASE_MS`); a run that crashes mid-send leaves a `sending` row that a later run reclaims once the lease expires, within the same three-retry budget. Rows left in `sending` by versions without a lease are not retried automatically. Email binding availability differs by deployment; see the configuration table in the self-hosting guide.

The same bundle also ships without Docker: on each published release, [.github/workflows/release-tarball.yml](.github/workflows/release-tarball.yml) attaches a tarball built by [scripts/package-tarball.mjs](scripts/package-tarball.mjs), laid out like the image's `/app`, with [docker/calends.service](docker/calends.service) keeping data in `/var/lib/calends` under the same relative path. [install.sh](install.sh), attached to each release and copied to the docs site, installs that tarball with a private Node under `/opt/calends-node` on Debian and Ubuntu; on upgrade it backs up the data directory first and restores both code and data if the new version fails its health check, and it never rewrites an existing `/etc/calends.env`. It does not configure domains or web servers.

Persist Docker's entire `/data` directory in a volume. It contains the SQLite database with its WAL files and the generated setup-token file; do not assume the database is a single file directly named `/data/calends.sqlite`. Building an image does not publish it. Registry destinations, tags and supported build platforms are configured by [.github/workflows/docker.yml](.github/workflows/docker.yml), while actual publication must be verified against the registry.

## Making a change

Use the [code standards](docs/code-standards.md#verification) for verification and PR evidence. Existing domain tests run with `npm test`; they are not a browser or Worker integration suite. Local development uses Vite on port 5173 and a Worker on port 8787, with API proxying defined in [app/vite.config.ts](app/vite.config.ts).

When a documented contract changes, update the owning section here alongside implementation and tests. Link source files and named functions instead of copying changing implementation details. Keep proposals separate from current behavior and state what has actually been exercised.
